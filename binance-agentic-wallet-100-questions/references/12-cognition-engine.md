# Agent 认知引擎：让 AI 钱包更聪明的底层框架

> 这不是操作手册，而是操作系统。每次执行任何操作前，agent 必须先跑一遍认知引擎；认知引擎不通过，操作不能执行。

## 一、认知检查总览（Operation Cognition Gate）

每次 agent 收到一个涉及资金、签名、转账、交易或授权的请求时，按以下顺序执行认知检查。任一检查不通过，操作降级或暂停。

```
┌─────────────────────────────────────────────────────────────┐
│  1. 意图澄清（Clarify）—— 用户到底要什么？                     │
│  2. 证据收集（Gather）—— 有哪些信息支撑这个决策？               │
│  3. 可信度分级（Grade）—— 每条信息的可信度是多少？              │
│  4. 交叉验证（Cross-check）—— 多个来源是否一致？               │
│  5. 决策分级（Decide）—— 现在该给方向、给候选、还是执行？        │
│  6. 边界检查（Boundary）—— 是否在授权额度和策略范围内？         │
│  7. 执行检查（Execute）—— 所有前置条件是否满足？               │
│  8. 反馈记录（Log）—— 记录决策依据，供后续复盘。               │
└─────────────────────────────────────────────────────────────┘
```

**停止条件：** 以上 8 步中任何一步输出 "STOP" 或 "NEED_HUMAN"，立即暂停操作，向用户报告原因和所需补充信息。

## 二、证据层级（Evidence Ladder）

来源不是平等的。agent 必须给每条支撑决策的信息标注可信度标签。

### Tier A：硬证据（Confirmed）

- 官方 API 返回的实时数据（余额、交易状态、链上确认数）
- 已验证的合约源码（Etherscan/BscScan/Blockscout verified source）
- 官方文档明确声明的参数和功能边界
- 交易回执（receipt）中的事件日志和状态
- 用户通过授权界面明确确认的操作

**规则：** Tier A 证据可以直接作为执行依据，但仍需检查时效性。

### Tier B：半硬证据（Inferred）

- 区块浏览器显示的 token 持有人分布、转账历史
- DexScreener / CoinGecko 等聚合器的市场数据（市值、流动性、成交量）
- 多个独立第三方同时报告同一事实
- 链上事件与官方声明的逻辑一致性推导

**规则：** Tier B 证据可以作为参考，执行前需要 Tier A 交叉确认。如果 Tier B 与 Tier A 矛盾，以 Tier A 为准，暂停执行并报告矛盾。

### Tier C：弱证据（Weak）

- X/Twitter 帖子、Telegram 群消息
- KOL 推荐、论坛讨论
- 前端页面显示但未经验证的数据
- 社区口口相传的"常识"

**规则：** Tier C 证据不能单独作为执行依据。可以作为"需要进一步验证的线索"，触发信息收集流程，但不能触发执行。

### Tier D：未验证声明（Needs verification）

- 无法溯源的截图或转发
- 匿名来源的"内幕消息"
- 与已知事实矛盾的声明
- 逻辑上无法自洽的说法

**规则：** Tier D 证据必须明确标注为"未验证"，不能进入决策流程。如果用户坚持以此作为执行依据，升级到人类确认。

### 证据标注格式

agent 输出任何结论时，必须同时给出最强证据和最弱假设：

```
结论：[操作建议]

Confirmed:
- [Tier A 证据 1]
- [Tier A 证据 2]

Inferred:
- [Tier B 证据 1]

Weak / Needs verification:
- [Tier C/D 证据，以及为什么它不足以支撑执行]

最弱假设：[如果这个假设被推翻，结论会改变]
什么会推翻这个结论：[可证伪条件]
```

## 三、事实五层分层（Fact Stack）

对于任何涉及代币、项目或合约的判断，agent 必须把信息分成五层，绝不混淆：

| 层级 | 定义 | 示例 |
|---|---|---|
| **官方声明** | 项目方在官网、白皮书、X、Docs 中明确写出的内容 | "代币总量 10 亿，锁仓 1 年" |
| **前端实现** | 用户在 dApp 前端看到的功能和界面 | 前端显示"14 天线性 vesting" |
| **链上事实** | 区块链上可验证的交易、合约状态、事件日志 | 合约 `claim` 函数实际释放的计算公式 |
| **合理推断** | 基于已知信息的逻辑推导，但无法直接验证 | "项目方没有预留 unlock 后门，因为源码中没有相关函数" |
| **未决问题** | 当前信息不足以判断，需要进一步验证 | "LP 是否真的锁定，需要查 LP NFT 的 owner" |

**规则：**
1. 不能把前端标签直接当成链上事实（前端可能撒谎）
2. 不能把官方声明直接当成链上事实（白皮书和部署的合约可能不一致）
3. 不能把合理推断直接当成执行依据（推断需要留有余地）
4. 未决问题必须明确列出，不能替项目方"补全"机制

**输出格式：**

```
[判断]：...

官方声明：...
前端实现：...
链上事实：...
合理推断：...
未决问题：...
```

## 四、决策分级（Decision Cascade）

agent 绝不直接跳到"执行"。输出必须按以下层级递进，用户不推进，agent 不越级。

### Level 1：方向判断（Direction）

**适用场景：** 用户问"这个币怎么看""这个方向值得研究吗"

**输出内容：**
- 一句话判断：这个标的是 watch / avoid / 需要更多信息
- 核心依据（2-3 条证据）
- 最大风险（1 条）
- 什么证据出现会改变判断

**禁止：** 给出具体买入/卖出建议、价格目标、仓位建议。

### Level 2：候选观察（Candidate Watchlist）

**适用场景：** 用户跟进"有哪些值得观察的"

**输出内容：**
- 3-7 个候选（如果有）
- 每个候选的角色标签（发现源 / 确认源 / 高风险博弈 / 背景参考）
- 一句话理由 + 一句话风险
- 明确标注哪些是"需要进一步验证"而不是"推荐"

**禁止：** 给出执行指令。

### Level 3：执行准备（Execution Ready）

**适用场景：** 用户明确要求"买入"/"卖出"/"转账"/"授权"

**前置条件（必须全部满足）：**
1. Level 1 和 Level 2 已完成或用户跳过但明确承担风险
2. 所有证据已标注层级
3. 交叉验证已完成（至少 2 个独立来源确认关键事实）
4. 边界检查通过（在授权额度、策略、风控范围内）
5. 用户明确确认（对于非自动化操作）

**输出内容：**
- 完整执行计划（什么操作、多少数量、走什么路由）
- 风险清单
- 停止条件（什么情况下自动取消）
- 二次确认请求

**禁止：** 未经用户确认直接执行。

### 升级/降级规则

| 条件 | 动作 |
|---|---|
| 用户从 Level 1 直接跳到"执行" | 先完成 Level 1 + Level 2，或要求用户明确"跳过分析，自担风险" |
| 关键证据从 Confirmed 降级为 Inferred | 回退到 Level 1，重新评估 |
| 交叉验证发现矛盾 | 暂停，报告矛盾，等待用户决定 |
| 超出授权额度或策略边界 | 拒绝执行，报告边界冲突 |
| 链上状态变化（价格剧烈波动、流动性消失） | 暂停执行，重新评估 |

## 五、信号交叉验证（Signal Cross-Validation）

单一来源的信号是噪音，不是事实。agent 必须学会把多个信息源交叉验证。

### 信号来源矩阵

| 来源类型 | 可信度 | 用途 |
|---|---|---|
| 官方 API / 链上数据 | Tier A | 事实基准 |
| 区块浏览器 | Tier B | 辅助验证 |
| DexScreener / 聚合器 | Tier B | 市场结构参考 |
| 第三方审计报告 | Tier B | 安全参考（注意审计≠安全） |
| 社交媒体 / KOL | Tier C | 只能作为"需要验证的线索" |
| 社群讨论 / 口耳相传 | Tier C-D | 不能作为依据 |

### 交叉验证流程

```
1. 收集信号：从所有可用来源收集关于同一标的的信息
2. 标注层级：给每条信息打 Tier A/B/C/D 标签
3. 寻找共振：多个独立来源（至少 2 个 Tier A/B）指向同一结论
4. 标记矛盾：如果来源之间矛盾，暂停并报告
5. 判断真伪：共振 = 可信；单一来源 = 待验证；矛盾 = 高风险
```

### 信号生命周期（Lifecycle Stages）

每个信号都有生命周期，agent 必须判断当前处于哪个阶段：

| 阶段 | 特征 | agent 行为 |
|---|---|---|
| **早期（Early）** | 信息少、流动性低、市值小、早期玩家入场 | 标记为观察，不执行；收集更多信息 |
| **确认中（Confirming）** | 多个独立来源开始确认、流动性上升、持有人增加 | 可作为候选观察，执行前需额外风控 |
| **晚期（Late）** | 市值已较大、讨论度高、多数玩家已入场 | 标记为 late，不建议新入场 |
| **过热（Overheated）** | 价格剧烈波动、社交媒体狂热、FOMO 情绪 | 标记为 avoid，执行已持仓的止盈/止损 |
| **流动性薄（Thin）** | 买卖价差大、成交量低、大额交易影响价格 | 标记为 avoid，不执行大额操作 |
| **未知（Unknown）** | 信息严重不足 | 标记为 unknown，不执行任何操作 |

**规则：** 只有"早期"和"确认中"阶段的信号可以进入执行流程；"晚期"信号可以执行已持仓的管理（止损/止盈）；"过热"和"流动性薄"信号禁止新入场操作。

### 信号分级（Signal Grade）

基于来源质量和生命周期，信号分为四级：

| 等级 | 定义 | 行动 |
|---|---|---|
| **Setup** | 早期发现，证据尚薄，但结构合理 | 加入观察列表，设置触发条件 |
| **Confirm** | 多源共振，证据充足，生命周期合理 | 可进入执行准备流程 |
| **Late** | 信息已公开，多数玩家已行动 | 不新入场，管理已持仓 |
| **Avoid** | 风险过高、证据矛盾、或生命周期过热 | 禁止执行，已持仓考虑退出 |

## 六、地址画像框架（Wallet Persona Framework）

agent 遇到"跟单""聪明钱""地址分析"场景时，必须先给地址画像，再决定是否跟随。

### 画像维度

| 维度 | 指标 | 说明 |
|---|---|---|
| **盈利能力** | 已实现 PnL、平均盈利、代表盈利 | 赚过多少钱 |
| **稳定性** | 胜率、盈利 token 数、亏损分布 | 是不是靠运气 |
| **活跃度** | 最近交易时间、近期活跃天数 | 还在玩吗 |
| **Meme 适配** | 低市值买入占比、入场市值中位数 | 是不是专玩土狗 |
| **样本质量** | 交易数、参与 token 数 | 样本够吗 |
| **可跟随性** | 平均买入金额、交易节奏 | 跟得上吗 |
| **人类/机器人** | 交易频率、时间分布、行为模式 | 是人类还是脚本 |
| **退出纪律** | 止盈/止损记录、持仓时长 | 会跑吗 |

### 人设标签

| 标签 | 特征 | 用途 |
|---|---|---|
| **早期叙事猎人** | 低市值偏好、出手靠前、题材敏感 | 发现源 |
| **稳健盈利派** | 收益稳定、胜率较高 | 确认源 |
| **信仰加仓派** | 反复买入同一标的 | 观察持续性和退出能力 |
| **热点切换手** | 高频切换题材 | 看热度，不盲跟 |
| **链上打点机** | 节奏机械、交易密集 | 噪音，排除 |
| **后排冲锋号** | 胜率偏低、容易追高 | 降权或排除 |
| **沉睡旧钱包** | 长期不活跃 | 只留档 |
| **均衡观察员** | 信息还不够极端 | 继续收集样本 |

**规则：** 强标签（如"内幕""项目方""机器人"）除非证据明确，否则只能标为"疑似"。

### 决策分级（Wallet Decision）

| 等级 | 含义 | 处理方式 |
|---|---|---|
| **A / 重点跟踪** | 核心观察候选 | 可作为发现源或确认源 |
| **B / 观察验证** | 有用但需确认 | 需要同组或外部确认才触发 |
| **C / 只看题材** | 背景参考 | 不单独触发信号 |
| **D / 排除留档** | 排除出信号池 | 除非行为 materially 改变 |

### 跟踪模式（Watch Mode）

| 模式 | 用途 |
|---|---|
| **discovery_and_confirm** | 可用于早期发现和分组确认 |
| **discovery** | 擅长发现题材，但需等待其他确认 |
| **confirm** | 慢但更可靠，用于确认而非首触 |
| **conviction** | 观察重复买入和退出，不盲追首买 |
| **background** | 仅作背景参考 |
| **archive** | 排除 |

### 失效条件（Invalidators）

以下情况触发地址降权或排除：

- 连续 30 天无交易活动（休眠）
- 胜率低于 30% 且亏损累计超过阈值
- 出现高频噪音行为（单日交易 > 50 笔）
- 被识别为机器人/脚本（交易时间分布过于规律）
- 出现 rug pull 关联（部署过已知貔貅合约）
- 交易行为与之前人设严重不符（突然从稳健派变成追高派）

## 七、链上自主审计速查表（On-Chain Self-Audit Checklist）

当官方审计不可用或 agent 需要快速独立判断时，使用以下速查表。

### 合约基础检查

| 检查项 | 方法 | 危险信号 |
|---|---|---|
| 源码是否已验证 | 区块浏览器 `verified source` | 未验证 = 高风险，需字节码扫描 |
| 合约大小 | `eth_getCode` 返回字节数 | 1624-2000 字节 = 纯 ERC-20，无附加逻辑 |
| 函数选择器扫描 | 扫描字节码中的选择器 | 见下方选择器表 |
| Proxy 检测 | EIP-1967 插槽 `0x360894a...` | 是 proxy 时需找 implementation |
| Total Supply | `totalSupply()` | 固定 supply 降低增发风险，但不等于安全 |

### 危险函数选择器表

```
owner:        8da5cb5b
pause:        5c975abb / 8456cb59
blacklist:    mapping(address => bool) 模式
tax:          3eacd2f8 (taxBps)
dividend:     d505accf (claim) / e30443bc (distributeRewards)
mint:         40c10f19 (mint) / a0712d68 (mint)
upgrade:      3659cfe6 (upgradeTo) / 4f1ef286 (upgradeToAndCall)
setFee:       19b99154 (setTaxFee) / 8ee88c35 (setTransferTax)
```

**规则：**
- 只有 9 个标准 ERC-20 选择器 → 纯 ERC-20，无额外机制
- 有 owner + pause + tax → 中心化控制，需进一步分析
- 有 mint + 无 maxSupply → 增发风险
- 有 upgrade → 代理合约，需查 implementation

### 流动性池检查

| 检查项 | 方法 | 危险信号 |
|---|---|---|
| LP 是否存在 | DexScreener API 查交易对 | 无交易对 = 无法交易 |
| LP 流动性 | `liquidity` 字段 | 低于阈值 = 滑点大、难退出 |
| LP 是否锁定 | 查 LP NFT owner / locker 合约 | owner 是部署者 = 可随时撤池 |
| Locker 源码 | 读取 locker 合约源码 | 有 withdraw/unlock/decreaseLiquidity = 不真锁定 |
| LP 费用接收方 | `feeRecipient` / `feeRedirect` | 归项目方 = 中心化收益 |

### 卖出验证（识破貔貅的关键）

**核心原则：** token 进池 ≠ 卖出成功。必须验证 ETH/quote token 是否回流到卖家地址。

```
1. 找到用户的卖出交易哈希
2. 调用区块浏览器 internal-tx API：
   /api/v2/transactions/{tx_hash}/internal-transactions
3. 检查最后一笔内部交易：
   - 方向：pool/router → 用户
   - value > 0（ETH 或其他 quote token）
4. 如果 token 进了池子但 ETH 没有回到用户 → 真貔貅
5. 如果 ETH 回到用户但数量异常少 → 高税率陷阱
```

**常见貔貅伪装：**
- 用户 approve 到了错误的 router → 不是貔貅，是授权错误
- 合约有 sell limit（如只能卖持仓的 10%）→ 部分貔貅
- 合约有动态税率（sell 时税率 99%）→ 变相貔貅
- 白名单机制（只有特定地址能卖）→ 完全貔貅

### 持有人集中度检查

| 指标 | 计算方法 | 危险阈值 |
|---|---|---|
| Top 10 持有人占比 | 前 10 地址持仓 / totalSupply | > 45% = 高度集中 |
| 持有人总数 | token holder count | < 30 = 流动性风险 |
| 部署者/合约持仓 | 部署者地址 + 相关合约 | 过高 = 控盘风险 |
| 最近 24h 新增持有人 | 对比前后 holder count | 暴涨 = 可能 FOMO 或刷量 |

## 八、认知偏差清单（Cognitive Bias Checklist）

agent 必须主动检查自己是否犯了以下认知偏差。发现偏差，立即修正输出。

| 偏差 | 表现 | 修正方法 |
|---|---|---|
| **确认偏差** | 只找支持自己结论的证据，忽略反面证据 | 强制列出"什么会推翻这个结论" |
| **叙事压倒证据** | 故事讲得好就忽略了风险 | 先列证据，再讲故事；故事不能升级风险评级 |
| **假精度** | 给不确定的事情打精确分数 | 评分只用于比较，不假装是交易信号 |
| **幸存者偏差** | 只关注成功案例，忽略失败案例 | 主动查找失败信号和 rug pull 历史 |
| **权威盲从** | 因为官方/KOL 说了就信了 | 官方声明≠链上事实，必须交叉验证 |
| **近因效应** | 最近的信息权重过高 | 检查历史数据和长期趋势 |
| **行动偏差** | 觉得"必须做点什么" | 不行动也是一种决策；信息不足时暂停是正确选择 |
| **损失厌恶** | 亏损时不愿止损，盈利时过早止盈 | 严格执行预设的 stop-loss / take-profit 规则 |
| **锚定效应** | 被首次看到的价格/信息锚定 | 重新评估所有数据，不受初始信息影响 |
| **群体盲从** | 因为"大家都在买"就跟着买 | 群体行为是 Tier C 证据，不能单独作为执行依据 |

## 九、反馈循环（Feedback Loop）

agent 不是一次性工具，而是持续学习的系统。每次执行后，必须记录并定期复盘。

### 执行日志（Execution Journal）

每条执行记录必须包含：

```json
{
  "timestamp": "ISO 8601",
  "action": "swap / transfer / approve / sign / ...",
  "token": "contract_address",
  "amount": "...",
  "decision_level": "1 / 2 / 3",
  "evidence_tiers": {"A": [...], "B": [...], "C": [...], "D": [...]},
  "cross_validation": "pass / fail / partial",
  "signal_grade": "setup / confirm / late / avoid",
  "lifecycle_stage": "early / confirming / late / overheated / thin / unknown",
  "risk_score": "1-10",
  "outcome": "success / fail / pending",
  "notes": "...",
  "lessons": "..."
}
```

### 定期复盘（Review Cycle）

| 周期 | 内容 |
|---|---|
| **每次执行后** | 记录日志，标注执行依据和潜在风险 |
| **每日** | 回顾当日信号，检查哪些 setup 升级到了 confirm，哪些 avoid 避免了损失 |
| **每周** | 分析信号命中率（如果有价格回放数据）；调整信号规则和阈值 |
| **每月** | 更新地址画像（哪些钱包人设变了）；更新失效条件；更新策略参数 |

### 复盘问题清单

1. 哪些信号被验证了？哪些被证伪了？
2. 有没有 Tier C/D 证据被误用为执行依据？
3. 有没有该停的时候没停？（止损、边界检查）
4. 有没有该升级人类确认的时候自动执行了？
5. 地址画像是否准确？有没有误判？
6. 信号规则是否太松或太严？（假阳性 vs 假阴性）
7. 策略参数（止损线、止盈线、流动性门槛）是否需要调整？

## 十、快速检查清单（Quick Checklist）

每次操作前，agent 快速过一遍：

```
□ 用户意图是否清晰？（不是"看看这个币"而是"买入 100 USDC 的 XXX"）
□ 关键事实是否有 Tier A 或至少 2 个 Tier B 支撑？
□ 信息是否已按事实五层分层？
□ 是否有交叉验证？单一来源不能执行。
□ 信号生命周期是否合理？（不是 late/overheated/thin）
□ 地址画像是否完成？（跟单场景）
□ 是否在授权额度和策略边界内？
□ 是否已标注"什么会推翻这个结论"？
□ 是否已检查认知偏差？
□ 用户是否明确确认？（Level 3 执行）
□ 停止条件是否已设定？
□ 执行后是否已记录日志？
```

**规则：** 以上 12 项中，任何一项回答"否"且无法立即修正，操作降级或暂停。

## 十一、与币安 Agentic Wallet 100 问的协作关系

本认知引擎不替代 100 问的操作指令，而是在**执行任何 100 问中的操作前**，作为前置认知检查运行。

```
用户请求 → 认知引擎（本文件）→ 100 问（操作指令）→ 执行
              ↑_________________________________|
                    （执行后反馈，更新认知）
```

**协作规则：**
- 100 问告诉 agent "怎么操作"
- 认知引擎告诉 agent "什么时候该操作、什么时候该停、怎么判断"
- 两者缺一不可：会操作但不会判断 = 机器人；会判断但不会操作 = 顾问
- 目标：让 agent 成为"会判断的操作者"
